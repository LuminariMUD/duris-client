# Releasing

## Version numbers

Versions follow [Semantic Versioning](https://semver.org): `MAJOR.MINOR.PATCH`, automatically tagged as `vMAJOR.MINOR.PATCH`. `build.py` and the release workflow reject any other shape. Mudlet does not interpret the string, so the meaning is a project convention:

| Bump | When |
| --- | --- |
| **MAJOR** | Players must reinstall or reconfigure: layout rebuilt, saved settings or aliases incompatible, package renamed, minimum Mudlet version raised. |
| **MINOR** | New panels, commands, or mapper features; behaviour changes that do not break an existing install. |
| **PATCH** | Bug fixes, GMCP field corrections, visual tweaks, docs inside the package. |

Pre-release tags such as `v2.0.0-rc.1` are not supported by the workflow; cut them as ordinary patch releases if needed.

## How it works

Every push to `master` runs [CI](../.github/workflows/ci.yml). After both package validation and the [real Mudlet offline suite](../.github/workflows/mudlet-runtime.yml) pass, CI calls the [release workflow](../.github/workflows/release.yml). Pull requests run the checks without publishing.

The release workflow uses [scripts/release.py](../scripts/release.py) to:

1. Read `VERSION` and require a matching, nonempty changelog section.
2. Build the package with Lua 5.1 and XML validation, then compare its contents against the committed `.mpackage`. ZIP timestamps are ignored; filenames and file contents must match.
3. Create the annotated `v<VERSION>` tag at the commit tested by CI.
4. Create a draft, upload both package filenames and checksums, then publish it as the latest release.

Already published versions are left intact. Documentation and workflow changes with the same `VERSION` do not create another release. If package sources changed since that version's tag, publishing fails and asks for a version bump. Existing tags are never moved. Publishing runs are serialized, and an older run cannot replace a newer version as the latest release.

The workflow uses GitHub's built-in `GITHUB_TOKEN` with `contents: write` only for publishing; no personal access token or additional secret is needed. It creates the release in the same job that pushes the tag because [events generated by `GITHUB_TOKEN` do not trigger another push workflow](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow). Publishing is restricted to `master` in `LuminariMUD/duris-client`.

## Cut a release

Publish to `LuminariMUD/duris-client`. Use `origin` as the only remote, pointing at that repository; check `git remote -v` before pushing. Repository-only documentation changes do not require a package version bump.

1. Bump `VERSION` (for example `1.2.0`) following the table above. Do not edit `src/config.lua` or `ArjUI.VERSION` by hand.
2. Add a `## 1.2.0 - YYYY-MM-DD` section to `CHANGELOG.md`. Its heading must equal `VERSION` exactly; the workflow copies that section into the release notes.
   For runtime changes, run `python3 scripts/mudlet_suite.py` using the
   [Linux setup](LINUX_DEVELOPMENT.md#automated-offline-tests), inspect the
   screenshots and Errors view, and record affected live/compatibility checks
   in the [testing log](ongoing-projects/mudlet-local-testing.md). CI's automated
   result does not replace visual review or establish Mudlet 4.19.1 coverage.
3. Rebuild and commit everything together:

   ```bash
   python3 build.py
   git add VERSION CHANGELOG.md duris-client.mpackage src
   git commit -m "Release 1.2.0"
   git push origin master
   ```

4. Watch the run under **Actions → CI**, including **Publish unreleased version / Tag and publish**. No manual tag is needed. When it finishes, the release appears at <https://github.com/LuminariMUD/duris-client/releases> with:
   - `duris-client.mpackage` (stable name; the README download badge points at the latest release)
   - `duris-client-1.2.0.mpackage` (versioned copy)
   - `SHA256SUMS.txt`

To validate the release files locally before pushing:

```bash
python3 -m unittest discover -s tests/release -v
python3 scripts/release.py --output /tmp/duris-release
```

This requires `lua5.1`, writes the package copies, checksums, and notes to the specified directory, and does not contact GitHub. The output directory must be separate from the repository root. Runtime and visual checks still apply as described above.

## Retry or fix a release

- If validation fails, fix the reported problem and push to `master` again.
- If tagging or uploading is interrupted, choose **Re-run failed jobs** on the CI run. A matching existing tag is reused and an incomplete draft is resumed. No partially uploaded draft becomes public.
- To retry the current `master` from scratch, choose **Actions → CI → Run workflow** with branch `master`. Both checks run again before publishing.
- To change an already published package, bump `VERSION`, add its changelog entry, rebuild, commit, and push. Do not delete or move published tags to reuse a version.
- A published release missing assets fails with a diagnostic for manual inspection; automation does not silently replace public downloads.

The standalone **Mudlet runtime → Run workflow** is available for diagnostics; it never publishes a release. CI keeps runtime screenshots as artifacts for manual review.
